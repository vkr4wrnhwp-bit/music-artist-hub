# MX LAB — TelemetryHardwareAdapter Specification

Purpose: Define the read-only TypeScript adapter contract that all telemetry hardware (simulated today, MX Node in future phases) must implement.

Status: Phase 1 — only the simulated adapter exists. All hardware adapters are future work, pending physical verification of the underlying data sources.

---

## 1. Boundary

Adapters are **read-only**. The interface deliberately contains no method that could control fueling, ignition, throttle, map slots, or any engine behavior, and no such method may ever be added to this interface. Hardware behind this interface is strictly passive: its failure must not affect the motorcycle (see `docs/safety/safety-boundary.md`).

## 2. Interface

```ts
interface TelemetryHardwareAdapter {
  /** Stable identity: adapter kind, hardware serial (if any), firmware label. */
  identify(): Promise<AdapterIdentity>;

  /** Declared capabilities; the UI renders only what is declared AND verified. */
  getCapabilities(): Promise<AdapterCapabilities>;

  /** Establish a session with the device (dock link, cable). Never touches the bike's ECU. */
  connect(): Promise<void>;
  disconnect(): Promise<void>;

  /** Channel catalog for this device in its current configuration. */
  getChannelDefinitions(): Promise<ChannelDefinition[]>;

  /** Start/stop local logging on the device. Logging is observation only. */
  startLogging(session: SessionDescriptor): Promise<void>;
  stopLogging(): Promise<SessionSummary>;

  /** Pull a completed session (chunked, resumable). */
  downloadSession(sessionId: string, onChunk: (c: TelemetryChunk) => void): Promise<SessionManifest>;

  /** Device self-diagnostics: storage, battery, GPS lock, sensor health, sync quality. */
  getDiagnostics(): Promise<AdapterDiagnostics>;
}
```

There are intentionally no methods for: writing configuration to an ECU, transmitting on any vehicle bus, actuating anything, or altering map state. Adding one is a safety-boundary violation.

## 3. ChannelDefinition schema

```ts
interface ChannelDefinition {
  name: string;                    // e.g. "rpm", "gps.speed"
  source: ChannelSource;           // "ecu-passive" | "gps" | "imu" | "analog" | "digital" | "simulated"
  unit: string;                    // UCUM-style, e.g. "rpm", "km/h", "degC", "mm"
  sampleRateHz: number;            // declared nominal rate
  dataType: "f32" | "f64" | "i16" | "i32" | "u16" | "u32" | "bool";
  scale: number;                   // physical = raw * scale + offset
  offset: number;
  validRange: { min: number; max: number };   // outside → quality "Out of range"
  quality: SignalQuality;          // current/last-known state, see Section 4
  calibration?: CalibrationRecord; // method, date, operator, reference
  timestampSource: "session-clock" | "gps" | "device-rtc";
  verification: VerificationStatus; // per docs/vortex/integration-boundary.md ladder
}
```

Notes:

- Any channel whose meaning derives from the Vortex ECU stays `Unverified` until the ladder in `docs/vortex/integration-boundary.md` is climbed with evidence. Channel lists, rates, and scalings for Vortex units are targets to validate, never assumed.
- `calibration` is required for analog sensors (suspension travel, clutch position) before their quality can be anything better than `Uncalibrated`.

## 4. Signal-quality states

| State | Meaning |
|---|---|
| Connected | Source present, data flowing within declared parameters |
| Missing | Source expected but absent (unplugged, dead) |
| Intermittent | Dropouts above threshold within the session |
| Out of range | Values outside `validRange`; data retained but flagged |
| Uncalibrated | No valid calibration record for a channel that requires one |
| Low confidence | Plausibility checks failed (e.g. cross-sensor disagreement); human review advised |
| Simulated | Data generated by a simulator; never mixable with real data unlabeled |
| Validated | Quality-reviewed against calibration and plausibility checks; highest state |

Quality is recorded per channel per chunk. Analysis views must display quality; charts render degraded-quality spans visually distinct.

## 5. Simulated adapter contract

The Phase 1 `SimulatedTelemetryAdapter`:

- Must always self-report simulation: `identify()` returns `kind: "SIMULATION"`, every channel reports `source: "simulated"` and quality `Simulated`, every chunk's provenance carries `simulated: true`.
- Must be deterministic: same seed + same scenario → identical output (required for testing gates, charts, and the AI Race Engineer).
- Must emulate the full contract, including diagnostics and degraded-quality scenarios (dropouts, out-of-range, missing GPS), so downstream handling is exercised before real hardware exists.
- Must never present itself as any real device, and the UI must label simulated sessions as SIMULATION at all times.

## 6. Compliance checklist for any future adapter

- [ ] Implements the interface with no additional control-capable methods
- [ ] Every ECU-derived channel carries a verification status from the ECUDefinition ladder
- [ ] Failure of the device demonstrably has no effect on engine operation (per-model-year physical verification)
- [ ] Provenance and sync-quality recorded per chunk
- [ ] Diagnostics report storage, battery, and sensor health honestly (no optimistic defaults)
